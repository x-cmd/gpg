# 年度密钥策略详解

团队的供应链密钥策略从外部看有点不寻常 —— 两把发布密钥而
非一把，其中一把每公历年轮换一次，但密码学上却设为永不过
期。本文是长文版推理。逐项展开为何策略是这个形状、每个
设计决策防范什么、有意留下的"空隙"在哪里。

## 两密钥模型

每次发布同时发两个签名制品：

| 制品                                    | 签名密钥     | 用途                                                                |
| ---                                    | ---           | ---                                                                |
| `x-cmd.rpm` / `x-cmd.deb`               | `official`    | 社区版。一次导入，未来升级静默验证。                                |
| `x-cmd-annual-<year>.rpm` / `.deb`      | `key-<year>`  | 合规版。为金融 / 政企审计的逐年隔离。                                |

两把密钥都在本仓库 `keyring/` 下，都在 `index.tsv` 中记
录，都汇总进 `keyring/keyring.asc`。团队同时发布两把，是
因为两类受众有不同的威胁模型与运营约束 —— 塞进一把密钥
会迫使一方接受另一方的权衡。

社区版优化 **零摩擦升级**。用户装一次包，主密钥被导入
种下，后续每个包（安全补丁、point release、版本升级）静
默校验，没有"每年续密钥"的杂务，也没有某日未值守主机突
然开始签名校验失败的日历边界。

企业 / 合规版优化 **严格逐年可审计**。金融或政企团队需
要能说"我们 2026 年部署的所有东西都由 2026 年隔离密钥签
名，那把密钥从未签过 2025 或 2027 的任何东西"。代价是一
年一次的密钥轮换；收益是逐年审计追踪干净。

## 密码学"永不过期"，运营"年度"

策略中最违反直觉的部分是年度密钥的过期设置：**没有**
过期。密码学上，私钥被设为永不过期。运营上，团队把它当
作过期处理 —— `key-2026` 私钥只签 2026 的制品，年边界
上团队"封存"它（让它不能再签新东西），并切到 `key-2027`。

两个对立力量驱动这一选择：

### 密码学卫生要求硬过期

标准 GPG 实践是在密钥上设置过期日期，以便最坏情况下
（密钥被攻陷）损害在时间上有界。过期之后，即便攻击者拿
到私钥也不能伪造客户端会接受的签名（前提是客户端会查过
期）。

### 运营讨厌生产环境硬过期

在企业环境里，硬过期会形成硬 SLA 边界。密钥过期的瞬
间，每台装着被这把密钥签过制品的主机开始失败日常安全扫
描的 `gpg --verify` —— 包括正在升级中、回滚中、或单纯
未值守的主机。未值守的生产环境里凌晨 2 点的"key expired"
告警，是一场注定发生的寻呼事件，是一场注定会被提起的
服务积分纠纷。

### 取舍

团队选两者之优：**密码学上无过期，运营上严格隔离**。
`key-2026` 私钥在线缆层永不过期；装着跨 2026 → 2027 边界
制品的客户端照旧校验两端。但团队在年末物理封存密钥，让
它不能再签新东西，并由一把全新的 `key-2027` 接管 2027
的制品。每个年度边界检查的产物都干净：没有制品同时被两
把密钥签过。

消费者在跨边界校验制品时永远碰不到"key expired"错误，
但每个年度边界上的审计日志都明确说出"哪把密钥签了什么"。

## 为什么不取 398 / 397 / 380 天

这些数字 —— 尤其是 398 —— 绑在 Web PKI 生态（SSL/TLS
证书）上。CA/Browser Forum 在 2026 年把公开 TLS 证书寿
命压到了 200 天以内。代码签名是另一个生态，不受那条时间
线约束，但在代码签名语境里复用旧的 398 天数字会被读成
"从错误标准里复制粘贴"。眼尖的安全审核员会把整体安全
姿态评审判定为"团队不理解哪个标准适用于哪个场景"。

干净的"按公历年度"边界（商业上 `365 天`，密码学上"永
不过期"）读起来是深思熟虑的。它也对齐了金融 / 政企采购
团队已经按年度审计周期组织的节奏 —— 技术轮换对齐业务
年度，对非技术利益相关方也容易解释。

## 跨年轮换时不要自动删除旧密钥

如果消费者的自动化在年度边界上删除旧年度密钥，那么每台
装着老制品的主机会在日常签名扫描中失败（"signed-by-key
unknown"），一次例行安全扫描就演变成生产事故。

团队的立场是：两把密钥都保留。仓库同时发布当前密钥
（在 `keyring/`）与历年年度密钥（在 `keyring/archive/`）。
消费者可以跨边界校验制品，永远碰不到"key missing"错
误。

如果某个合规制度要求最终裁剪历史密钥，那是运营方在他们
自己主机上的判断 —— 团队不表态。"与你的合规不兼容"这口
锅归作出选择的那一方。

## 重签发机制（LTS 客户）

2027 年的付费企业客户想装 2025 年的制品。制品原始签名
是 `key-2025` 签的，他们可能已导入也可能没。即使已导入，
他们可能希望用 `key-2027` 重签，让 2027 年的审计日志干
净。

团队通过 **重签发生命周期（repackage / resign
lifecycle）** 支持这一点：在不重编译、不修改上游二进
制的前提下，给老制品用当前年度密钥加新签名。CI workflow
对现有 release 资产跑 `rpmsign --addsign`，给二进制文件
打上新签名头；包内字节不变。重签包作为新制品发布，原版
（key-2025 签）与重签版（key-2027 签）都留在 release 历
史里。

### 免费 vs 付费的边界

重签老制品公开托管（透明度是价值主张的一部分）。但 *哪
些历史版本重签、多久重签一次* 由服务等级决定。团队不为
免费用户维护老版本的重签。长期支持（LTS）的重签是付费
订阅功能 —— 金融 / 政企客户按合同付费，换取"请把 2024
的某个制品用今年密钥重签一次"的请求权。

定价线是有意为之：免费用户只要持有对应历史密钥就能校验
任何历史制品（我们永久保留在 `keyring/archive/`），付费
LTS 用户则不用自己维护逐年密钥清单，享受"每个制品都带
当前我正在用的密钥签名"的便利。

## 这些如何映射到 `index.tsv`

两密钥策略全部住在这个仓库的清单里：

```tsv
handle          uid              fingerprint    created     purpose
official        Li Junhao …      AAAA…          2022-03-15  release-signing,package-signing
key-2026        Li Junhao …      BBBB…          2026-01-04  package-signing-yearly
key-2027        Li Junhao …      CCCC…          2027-01-04  package-signing-yearly
```

（以上在团队实际发布时填入。`key-2025` 及更早年份一旦
轮换就移入 `keyring/archive/`。）

要校验 `x-cmd-annual-2026.rpm` 的消费者：

```sh
# 直接拉 2026 年度密钥
curl -fsSL https://raw.githubusercontent.com/x-cmd/gpg/main/keyring/key-2026.asc \
  | gpg --import

# 确认 fingerprint 与 index.tsv 一致
awk -F'\t' '$1=="key-2026" { print $3 }' index.tsv

# 校验包
rpm -K x-cmd-annual-2026.rpm
```

要同时校验 `x-cmd.rpm`（社区版）与 `x-cmd-annual-2026.rpm`
（合规版）的消费者：

```sh
# 经汇总一次拉两把
curl -fsSL https://raw.githubusercontent.com/x-cmd/gpg/main/keyring/keyring.asc \
  | gpg --import

# 校验两个包
rpm -K x-cmd.rpm
rpm -K x-cmd-annual-2026.rpm
```

## FAQ

本文落在中心 FAQ 的"寿命 / 轮换"问题群的正中央。下面挑
出 4 条最相关的；完整的 8 问在
[文章 0](./0-x-cmd-gpg-overview.cn.md#faq--软件分发与代码签名密码学)，
答案以行业普遍视角书写，与具体项目无关。

### Q4：硬编码 GPG 密钥为"永不过期"有哪些优缺点？

权衡点是业务连续性与爆炸半径。永不过期意味着历史制品永
远能校验，CI/CD 永远不用轮换密钥 —— 零维护、未值守主机
不会因"密钥过期"出现故障；代价是一旦私钥被攻陷泄露，攻
击者获得无限期的伪造能力，恢复依赖发行后极难分发的"吊
销证书"机制。这正是"密码学永不过期 / 运营年度轮换"模
式试图拆分的权衡点。完整答案见文章 0。

### Q5：历史上许多证书 / 密钥的寿命为什么是 398 天或 397 天？

398 / 397 这两个数字绑在公开信任的 Web 证书（SSL/TLS）
上 —— 398 天是 CA/Browser Forum 自 2020 年起规定的一年
期 Web 证书最大寿命（365 天基线 + 33 天跨年 / 多时区缓
冲）；397 天是工程实践上的防御性退让，吸收全球扫描器几
小时时区漂移。这些数字不适用于代码签名 —— CA/B Forum 规
则覆盖 Web PKI，不覆盖包签名。代码签名通常采用 1 到 2 年
长期期。完整答案见文章 0。

### Q6：2026 年 SSL/TLS 证书标准发生了什么变化？代码签名受影响吗？

2026 年 3 月起，公开信任的 Web 证书上限压到 200 天以内
（2027 年将进一步压到 100 天左右）—— 目标是用自动化消除
长期密钥。代码签名明确豁免：国际根证书计划与 OS 级安全
审计规范把包签名与代码签名归类为基础设施锚点，不在 Web
证书寿命缩减计划的范围内。在 Linux 包分发与企业合规领域，
1 到 2 年长期轮换仍是主流实践。完整答案见文章 0。

### Q7：商业软件采用"一年一换"密钥隔离有哪些优缺点？

优势：安全与合规高 —— 年度轮换对齐多数金融 / 政企采购
要求的"年度安全审计"指标；即便某年私钥泄露，风险也完
全被封在当年版本内。劣势：老系统兼容性摩擦 —— 若老系统在
跨年时删除旧密钥，历史版本软件在日常依赖扫描中开始报错；
双重签名困境 —— 把两把密钥同时签入同一个 RPM，不同发行
版校验引擎解析逻辑不一致，生产环境易出错。完整答案见文章 0。

### Q8：采用"一年一换"模型，工业界如何解决跨年过渡与历史回滚？

标准模式是 **Trust Anchor Registry（信任锚点注册表）**，
杠杆点在用户侧的密钥环：发布方把所有历年年度公钥合并进
单个 keyring，消费者导入自己的 `gpg` 并在本地同时持有当
年与次年的密钥。`gpg` 密钥环是用户自己的；审计策略 ——
"保留这把、删除那把、按自定节奏轮换" —— 由用户在自己的
密钥环上定。这正是缓解 Q7 老系统兼容性摩擦与双重签名困
境的标准方案。完整答案见文章 0。
