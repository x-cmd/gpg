# Publishing your own GPG keyring

The pipeline from "team member has a new GPG keypair on their
laptop" to "row in `index.tsv` and bytes in `keyring.asc`"
is deliberately small — six gpg commands, a one-line
manifest update, and a CI pass. This article walks through
every step and explains why each one is shaped the way it is.

## The two-file layout

Before any of the pipeline, it helps to know what lands in
the repo:

```text
keyring/
  ├── <handle>.asc       # one file per published key
  └── keyring.asc        # the aggregate; concatenated on every release
index.tsv                # 5-column manifest
README.md / README.cn.md # front-of-page catalog, regenerated from index.tsv
```

`keyring/<handle>.asc` is the canonical artifact — that's
what a single-key consumer (`x gpg import <handle>`) fetches.
`keyring/keyring.asc` is the aggregate — that's what a
"import everything" consumer pulls in one HTTP GET.
`index.tsv` is the manifest that lets the README catalog,
`x gpg info`, and any tooling answer "what keys exist,
what fingerprint, what purpose, when created" without having
to parse OpenPGP packets.

## Adding a new key

The team-internal flow when a maintainer publishes a new key:

```sh
# 1. Maintainer exports their public key (ASCII-armored)
gpg --armor --export <KEYID> > keyring/<handle>.asc

# 2. Maintainer self-signs the export
gpg --detach-sign --armor \
    -u <signing-subkey> \
    keyring/<handle>.asc
# produces keyring/<handle>.asc.asc — kept off-repo,
# referenced in the commit text for the auditor's offline
# verification chain

# 3. Maintainer appends a row to index.tsv
#    handle<TAB>uid<TAB>fingerprint<TAB>YYYY-MM-DD<TAB>purpose

# 4. Maintainer opens a PR *internally* (the x-cmd monorepo,
#    not this public repo). A second team member reviews:
#    - gpg --list-packets keyring/<handle>.asc parses cleanly
#    - the fingerprint in index.tsv matches gpg --show-keys
#    - the .asc.asc detached signature verifies against the
#      signing subkey
#    - the key has a valid self-signature on its primary UID

# 5. On merge, the release pipeline regenerates
#    keyring/keyring.asc by concatenating all <handle>.asc
#    files in lexicographic handle order.
```

External contributors never see steps 4–5. The whole point
is that the team is the only path to a commit on `keyring/`
or `index.tsv` in this repo. External PRs that touch those
paths are closed without merge — see
[`CONTRIBUTING.md`](../CONTRIBUTING.md) for the policy text.

## Regenerating the aggregate

`keyring/keyring.asc` is **not** edited by hand. It's
regenerated by the release pipeline:

```sh
{
  for f in keyring/<handle>.asc; do
    cat "$f"
    echo ""                  # one blank line between concatenated keys
  done
} > keyring/keyring.asc
```

The script sorts by `handle` (matching the `index.tsv` order)
so the file is byte-stable across regenerations. The CI
workflow re-runs this script on every push to `main`; if the
regenerated `keyring.asc` differs from the committed one, the
push fails. That guarantees the aggregate file is always in
lockstep with the per-key files.

## CI checks (every push + every PR)

The GitHub Actions workflow in `.github/workflows/verify.yml`
runs on every push and every PR (with a read-only token for
external PRs so it can verify without granting write
access). The four checks, in order:

### 1. Parse check

```sh
gpg --list-packets keyring/keyring.asc
```

Exit code 0 → the file is well-formed OpenPGP packet stream.
A corrupted or truncated export fails here before anything
else gets checked.

### 2. Fingerprint-vs-manifest check

For every row in `index.tsv`, the listed fingerprint must
appear in `keyring/keyring.asc`. Drift (a manifest row
pointing at a fingerprint that isn't in the keyring, or
a fingerprint in the keyring with no manifest row) fails
the workflow.

### 3. Self-signature check

Every key in `keyring/keyring.asc` carries a valid
self-signature on its primary UID. This catches
half-exported keys (e.g. someone ran `gpg --export` while
the keyring was in a half-imported state and got a partial
export).

### 4. Uniqueness check

No two `index.tsv` rows share a fingerprint. No two
`keyring/*.asc` files share a fingerprint. Duplicate →
fail. This is the simplest possible check against the
"two near-identical keys, one is the impostor" attack.

The CI does **not** attempt to verify trust signatures or
web-of-trust paths — those are the consumer's
responsibility, using `x gpg` or upstream `gpg --check-sigs`.

## Key rotation

When a key expires or a team member rotates:

1. The team member publishes a **cryptographic transition
   statement** — a signed message from the *old* key
   stating "this key is being retired, new key is
   `<fingerprint>`". The statement is linked from the team's
   site, not committed here (keeps the repo small).
2. The old `keyring/<handle>.asc` is moved to
   `keyring/archive/<handle>.<created-date>.asc` in the next
   release commit. The current `keyring/<handle>.asc` is
   replaced by the new key.
3. `index.tsv` is updated in the same commit to reflect the
   rotation. The README's "Retired keys" table is
   auto-generated from `keyring/archive/` on every release.

A retired key is kept in the archive forever, **signed by
the team's primary key**, so consumers who already imported
the team's primary key can verify the chain of custody.
The retired key's fingerprint never reappears under a new
handle.

## What you (an external reader) can verify

If you want to confirm the team didn't sneak a malicious
commit into a release:

1. `git log` on `keyring/<handle>.asc` shows the file's
   history. Every commit message references the team member
   who added it and (ideally) the detached-signature
   filename for offline verification.
2. The CI workflow files in `.github/workflows/` are
   themselves in git — you can read them to see what checks
   the team runs against every commit.
3. The team's release tags are GitHub-signed (the
   `gh:x-cmd/gpg` repo's tags should carry the team's GPG
   signature on the tag object). Verify with
   `git tag --verify <tag>`.

None of these replace importing the key directly and
checking the fingerprint against an independent source — but
they do give you the audit trail.

## Scenario: signing RPMs with the published key

Once you've published your key, the most common follow-up
is using it to sign the artifacts you ship. For RPM-based
distributions, that's `rpmsign`.

### Prerequisites

You need three things:

1. **The team's signing private key** in your local GPG
   keyring. The matching public key is in
   [`keyring/<handle>.asc`](../keyring/); the private half
   is held by whoever is doing the signing (typically the
   release CI's secure secret store, or a build engineer's
   offline laptop).
2. **`rpm-build` and `rpm-sign` packages** installed:

   ```sh
   dnf install rpm-build rpm-sign gnupg2
   ```
3. **A built `.rpm` file** to sign.

### Importing the signing key

```sh
# From an exported private-key bundle
gpg --import /secure/path/to/team-signing-key.private.asc

# Confirm the import
gpg --list-secret-keys --keyid-format long
```

The output should list the team's key with both `pub` and
`sec` rows.

### Configuring rpmsign

Set the key explicitly in `~/.rpmmacros` so you don't rely
on `gpg-agent`'s "default key" guess:

```text
# ~/.rpmmacros
%_gpg_name  Team Name (Package Signing Key) <packages@example.com>
%_gpgbin    /usr/bin/gpg2
```

### Signing a single RPM

```sh
rpmsign --addsign /path/to/x-cmd-1.2.3-1.x86_64.rpm
```

`--addsign` *adds* a signature without removing existing
ones — useful for the LTS repackage workflow where you
want the artifact to carry signatures from both this year's
key and last year's. To replace all existing signatures,
use `--resign` instead:

```sh
rpmsign --resign /path/to/x-cmd-1.2.3-1.x86_64.rpm
```

### Batch signing (CI / multiple RPMs)

```sh
for rpm in /build/RPMS/*/*.rpm; do
  rpmsign --addsign "$rpm"
done
```

### Verifying

```sh
rpm -K /path/to/x-cmd-1.2.3-1.x86_64.rpm
```

Output should end with `OK`. For verbose output showing the
signing key's fingerprint and UID:

```sh
rpm -Kv /path/to/x-cmd-1.2.3-1.x86_64.rpm
```

Cross-check the signing key's fingerprint against
[`index.tsv`](../index.tsv) column 3 — that's the
"three-way fingerprint comparison" workflow.

### Passphrase handling in CI

`rpmsign` invokes `gpg` under the hood, which will prompt
for the signing key's passphrase on every invocation. For
human-driven signing, type the passphrase once. For CI /
batch, use either:

- **`gpg-agent` with a pre-loaded cache.** Start `gpg-agent`
  in your CI job before invoking `rpmsign`; preset
  the passphrase via `gpg-preset-passphrase`.
- **`--passphrase-file <path>`** passed to `rpmsign` (which
  forwards to `gpg`). Point at a file containing the
  passphrase. The file should be `chmod 600` and live in
  the CI's secret store.

### Common release pitfalls

- **"Public key not found" when running `rpm -K`**: import
  it (e.g., `rpm --import`).
- **Wrong key selected**: `rpmsign` uses whichever key
  matches `%_gpg_name` in `~/.rpmmacros`. Always set
  `%_gpg_name` explicitly in CI.
- **Multiple signatures**: `--addsign` adds a signature
  alongside existing ones — both verify. Use `--resign` for
  a clean release where only the current key is wanted.
- **Passphrase prompt in CI**: use `gpg-agent` or
  `--passphrase-file`.

## Putting it together (release CI)

A typical release job:

```sh
# 1. Import the team's signing key from CI secret store
echo "$TEAM_SIGNING_KEY_PRIVATE" | gpg --import --batch

# 2. Set up rpmmacros
cat > ~/.rpmmacros <<EOF
%_gpg_name  Team Name (Package Signing Key) <packages@example.com>
EOF

# 3. Pre-load passphrase into gpg-agent
echo "$TEAM_GPG_PASSPHRASE" \
  | gpg-preset-passphrase --preset $(gpg --list-secret-keys --with-colons \
                                       | awk -F: '/^sec/{print $5}')

# 4. Sign every RPM in the build output
for rpm in /build/RPMS/*/*.rpm; do
  rpmsign --addsign "$rpm"
done

# 5. Verify
rpm -Kv /build/RPMS/*/*.rpm

# 6. Publish to yum repo
createrepo --update /var/www/repo/
```

Each step is independently auditable: which key signed
(step 5 + cross-check vs `index.tsv`), what it signed (the
file list), when (the release tag).
