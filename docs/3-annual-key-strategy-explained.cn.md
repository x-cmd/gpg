# 年度密钥策略 —— 设计探讨

> **状态：探讨中。** 截至本文撰写时，团队尚未采用多密钥
> 发布流水线。本文走查的是一种 *候选* 设计 —— 两把密钥
> 的拆分看上去是什么、为何密码学上"永不过期"但运营上"年度
> 轮换"是站得住脚的形状、以及 repackage / resign 生命周期
> 如何工作 —— 作为分析提供，而非对当前已实施内容的描述。
> 请把本文余下部分视为"若团队采用此设计，行为会是什么样、
> 会带来哪些权衡"。

候选设计有两部分初看不太寻常：两把发布密钥而非一把，其中
一把每公历年轮换一次，但密码学上设为永不过期。本文是长文
分析。逐项展开为何设计是这个形状、每个设计决策防范什么、
有意的"空隙"会在哪里。

## 两密钥模型（候选）

按此设计，每次发布将寄出两个已签名制品：

| 制品                                    | 签名密钥     | 用途                                                                |
| ---                                    | ---           | ---                                                                |
| `x-cmd.rpm` / `x-cmd.deb`               | `official`    | 社区版。一次导入，未来升级静默校验。                                |
| `x-cmd-annual-<year>.rpm` / `.deb`      | `key-<year>`  | 合规版。为金融 / 政企审计的逐年隔离。                                |

两把密钥都将位于本仓库 `keyring/` 下，都记录在 `index.tsv`
中，都汇总进 `keyring/keyring.asc`。设计要求两者都发布，
是因为两类受众有不同的威胁模型与运营约束 —— 塞进一把密钥
会迫使一方接受另一方的权衡。

社区版将优化 **零摩擦升级**。用户装一次包，主密钥被导入
种下，后续每个包（安全补丁、point release、版本升级）静
默校验，没有"每年续密钥"的杂务，也没有某日未值守主机突
然开始签名校验失败的日历边界。

年度版将优化 **严格逐年可审计**。金融或政企团队需要能
说"我们 2026 年部署的所有东西都由 2026 年隔离密钥签
名，该密钥从未签过 2025 或 2027 的任何东西"。代价是一年
一次的密钥轮换；收益是逐年审计追踪干净。

## 密码学"永不过期"，运营"年度"

设计中最违反直觉的部分是年度密钥的过期设置：将是 **没有**
过期。密码学上，私钥被设为永不过期。运营上，它将被当作过期
处理 —— `key-2026` 私钥只签 2026 的制品，年边界上团队
"封存"它（让它不能再签新东西），并切到 `key-2027`。

两个对立力量驱动这一选择：

### 密码学卫生要求硬过期

标准 GPG 实践是在密钥上设置过期日期，以便最坏情况下
（密钥被攻陷）损害在时间上有界。过期之后，即便攻击者拿
到私钥也不能伪造客户端会接受的签名（前提是客户端会查过
期）。

### 运营讨厌生产环境硬过期

在企业环境里，硬过期会形成硬 SLA 边界。密钥过期的瞬
间，每台装着被这把密钥签过制品的主机开始失败日常安全扫
描的 `gpg --verify` —— 包括正在升级中、回滚中、或单纯
未值守的主机。未值守的生产环境里凌晨 2 点的"key expired"
告警，是一场注定发生的寻呼事件，是一场注定会被提起的
服务积分纠纷。

### 候选取舍

设计选两者之优：**密码学上无过期，运营上严格隔离**。
`key-2026` 私钥在线缆层永不过期；装着跨 2026 → 2027 边界
制品的客户端照旧校验两端。但团队在年末物理封存密钥，让
它不能再签新东西，并由一把全新的 `key-2027` 接管 2027
的制品。每个年度边界检查的产物都干净：没有制品同时被两
把密钥签过。

消费者在跨边界校验制品时永远碰不到"key expired"错误，
但每个年度边界上的审计日志都明确说出"哪把密钥签了什么"。

## 为什么不取 398 / 397 / 380 天

这些数字 —— 尤其是 398 —— 绑在 Web PKI 生态（SSL/TLS
证书）上。CA/Browser Forum 在 2026 年把公开 TLS 证书寿
命压到了 200 天以内。代码签名是另一个生态，不受那条时间
线约束，但在代码签名语境里复用旧的 398 天数字会被读成
"从错误标准里复制粘贴"。眼尖的安全审核员会把整体安全
姿态评审判定为"团队不理解哪个标准适用于哪个场景"。

干净的"按公历年度"边界（商业上 `365 天`，密码学上"永
不过期"）读起来是深思熟虑的。它也对齐了金融 / 政企采购
团队已经按年度审计周期组织的节奏 —— 技术轮换对齐业务
年度，对非技术利益相关方也容易解释。

## 跨年轮换时不要自动删除旧密钥

如果消费者的自动化在年度边界上删除旧年度密钥，那么每台
装着老制品的主机会在日常签名扫描中失败（"signed-by-key
unknown"），一次例行安全扫描就演变成生产事故。

设计的中间立场：仓库同时发布当前密钥（在 `keyring/`）与
历年年度密钥（在 `keyring/archive/`）。消费者可以跨边界
校验制品，永远碰不到"key missing"错误。这是我们留给用
户的自主性 —— 团队的职责到"把字节发出来"为止；运营方在
自己主机上决定策略。

如果某个合规制度要求最终裁剪历史密钥，那是运营方在他们
自己主机上的判断 —— 团队不表态。"与你的合规不兼容"这口
锅归作出选择的那一方。

## 重签发机制（候选）

企业客户在 2027 年想装 2025 年的制品。制品原始签名是
`key-2025` 签的，他们可能已导入也可能没。即使已导入，他
们也可能希望用 `key-2027` 重签，让 2027 年的审计日志干
净。

设计通过 **重签发生命周期（repackage / resign
lifecycle）** 支持这一点：在不重编译、不修改上游二进制
的前提下，给老制品用当前年度密钥加新签名。CI workflow 对
现有 release 资产跑 `rpmsign --addsign`，给二进制文件打
上新签名头；包内字节不变。重签包作为新制品发布，原版
（key-2025 签）与重签版（key-2027 签）都留在 release 历
史里。

### 重签按需处理

重签老制品公开托管，与原签版本并列，消费者按自己持有哪
些密钥选用。

按此设计，团队不会主动为每次发布把每个历史制品都重签；
只在客户提出具体需求时才会重签。任何人用 `keyring/archive/`
中对应的历史密钥都能校验历史制品 —— 这是 GPG 的默认能力，
不需要团队额外动作。需要团队代为完成重签工作的客户，可
通过支持渠道提出具体请求；某次重签能否做、做到多快，取决
于团队与该客户维护关系的具体约定。

## 这将 *如何* 映射到 `index.tsv`（示例）

两密钥设计将全部住在仓库清单里。**下表只是示例 —— 当前
`index.tsv` 中并无这些行。** 列出是为了展示：若团队采用
此设计，schema 会是什么样子：

```tsv
handle          uid              fingerprint    created     purpose
official        <uid>            <fingerprint>  <date>      release-signing,package-signing
key-2026        <uid>            <fingerprint>  <date>      package-signing-yearly
key-2027        <uid>            <fingerprint>  <date>      package-signing-yearly
```

按此设计，`key-2025` 及更早年份一旦轮换就移入
`keyring/archive/`。

要校验 `x-cmd-annual-2026.rpm` 的消费者：

```sh
# 直接拉 2026 年度密钥
curl -fsSL https://raw.githubusercontent.com/x-cmd/gpg/main/keyring/key-2026.asc \
  | gpg --import

# 确认 fingerprint 与 index.tsv 一致
awk -F'\t' '$1=="key-2026" { print $3 }' index.tsv

# 校验包
rpm -K x-cmd-annual-2026.rpm
```

要同时校验 `x-cmd.rpm`（社区版）与 `x-cmd-annual-2026.rpm`
（合规版）的消费者：

```sh
# 经汇总一次拉两把
curl -fsSL https://raw.githubusercontent.com/x-cmd/gpg/main/keyring/keyring.asc \
  | gpg --import

# 校验两个包
rpm -K x-cmd.rpm
rpm -K x-cmd-annual-2026.rpm
```
