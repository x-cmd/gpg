# Contributing

This page covers the **maintainer** side of the
[`x-cmd/gpg`](https://github.com/x-cmd/gpg) repo — the file
layout, how a key is published, how `index.tsv` is kept in sync
with the keys under `keyring/`, and what to do when a key expires
or is rotated.

## Read this first — maintenance policy

> **Like our other repositories, we humbly welcome guidance and
> feedback from friends.** Please open an
> [issue](https://github.com/x-cmd/gpg/issues) if you have
> suggestions — issues are public, reviewable, and feed into
> the team's documentation backlog. We don't pretend to have all
> the answers; we do want to hear what's broken, missing, or
> confusing.
>
> **But for security reasons, this repo does not accept pull
> requests from anyone outside the maintainer group.** This is
> the strong form of the rule — it applies to *every* file, not
> just `keyring/` or `index.tsv`. Doc fixes, typo corrections,
> link fixes, even README prose: all of those go through an
> issue first, and the team writes the commit. The repo is
> maintained by the x-cmd team only.

Why the strong form: every consumer of these keys — [`x gpg`](https://x-cmd.com/mod/gpg),
`apt`, `dnf`, package mirrors, release tarballs — treats the
fingerprint as a trust anchor. A PR that swaps a real
fingerprint for a look-alike one is a supply-chain attack,
not a contribution. Even doc-only PRs are funneled through
issues because the team prefers to write and own its own
public-key documentation in one voice, and because "an
external PR with no security implications" can only be
verified *after* it's been merged — by which point the
bytes are out.

Three concrete consequences for non-team contributors:

1. **Bug reports / typos / broken links / prose suggestions** —
   issue, not PR. The team writes the fix in their own
   commit.
2. **New key requests** (e.g. "could you add maintainer X?") —
   issue, with the maintainer's public key attached; the team
   decides whether to publish and writes the commit.
3. **Anything touching `keyring/*.asc` or `index.tsv`** —
   issue only; the team regenerates these from its own
   authoritative source.

## Repository layout

```text
.
├── keyring/                      # ASCII-armored public keys, one file per key
│   ├── <handle>.asc          #   filename = x-cmd handle (matches index.tsv)
│   └── keyring.asc           #   concatenated keyring, regenerated by the team
├── index.tsv                 # 5-column manifest: handle \t uid \t fingerprint \t created \t purpose
├── README.md                 # English — front-of-page key catalog (auto-inlined from index.tsv)
├── README.cn.md              # Chinese version
├── SKILL.md                  # AI-agent recipe for x gpg + gpg-key consumption
├── CONTRIBUTING.md           # this file
├── LICENSE                   # project license
└── .github/
    └── workflows/
        └── verify.yml        # on every push: gpg --list-packets + fingerprint check vs index.tsv
```

`keyring/keyring.asc` is **regenerated** from the per-key files on every
release commit by the team — do not expect the contents of two
files in the same commit to match byte-for-byte until the
regeneration step has run.

## A key is published like this

```sh
# 1. Team member exports their *current* public key (ASCII-armored)
gpg --armor --export <KEYID> > /tmp/<handle>.asc

# 2. Team member signs the export with the team's signing subkey
#    (this produces a detached .sig next to the .asc — not committed,
#    but referenced in the commit message so reviewers can verify
#    offline with `gpg --verify <handle>.asc.sig <handle>.asc`).

# 3. The team member opens a PR *internally* (the x-cmd monorepo),
#    adds `keyring/<handle>.asc`, regenerates `keyring/keyring.asc` and
#    `index.tsv`, and merges after a second-team-member review.
```

External contributors never see step 3. If you're outside the
team and want a key published, see "Read this first" above.

## `index.tsv` — 5 columns

| # | Column       | Meaning                                                        |
| - | ------------ | -------------------------------------------------------------- |
| 1 | `handle`     | x-cmd handle (matches `keyring/<handle>.asc`). Lowercase, no spaces. |
| 2 | `uid`        | The `Name (comment) <email>` published in the key's UID list.   |
| 3 | `fingerprint`| 40-char uppercase hex, no spaces. The trust anchor.            |
| 4 | `created`    | `YYYY-MM-DD` — date the key was created (per `gpg --list-keys --with-colons`). |
| 5 | `purpose`    | Short free-text: `release-signing`, `package-signing`, `mirror`, etc. |

Rows are ordered by `handle` (lexicographic, ASCII), so a plain
`sort` produces a stable diff. The README's per-key table is
generated from this file on every release commit by inlining the
table between `BEGIN/END keys.md` markers (same pattern as
`x-cmd/cve`'s report markers).

## Key rotation

When a key reaches its expiry date, or a team member leaves, or
a subkey is compromised:

1. The team member publishes a **cryptographic transition
   statement** — a signed message from the *old* key stating
   "this key is being retired, new key is `<fingerprint>`". The
   statement is linked from the team's site (not committed here,
   to keep the repo small).
2. The old `keyring/<handle>.asc` is moved to `keyring/archive/<handle>.<created-date>.asc`
   in the next release tag. The current `keyring/<handle>.asc` is
   replaced by the new key.
3. `index.tsv` is updated to reflect the rotation; the README's
   "Retired keys" table (auto-generated from `keyring/archive/`) gains
   one row.

Consumers are expected to pin to the *current* fingerprint, not
the handle — handles can be re-used after a rotation; fingerprints
cannot.

## CI

`.github/workflows/verify.yml` runs on every push to `main` and
on every PR (read-only token, so external PRs can be checked
without granting write):

1. **Parse check.** `gpg --list-packets keyring/keyring.asc` exits 0.
2. **Fingerprint check.** For every row in `index.tsv`, the
   fingerprint exists in `keyring/keyring.asc`. Drift → fail.
3. **Self-signature check.** Each key in `keyring/keyring.asc` carries a
   valid self-signature on its primary UID (catches half-exported
   keys).
4. **No duplicates.** No two `index.tsv` rows share a fingerprint.
   No two `keyring/*.asc` files share a fingerprint. Duplicate → fail.

The CI does **not** attempt to verify trust signatures or web-of-
trust paths — those are the consumer's responsibility, using
[`x gpg`](https://x-cmd.com/mod/gpg) or upstream `gpg --check-sigs`.

## What this repo is NOT

- **Not** a general-purpose GPG keyserver. We don't accept
  uploads; we don't mirror `keys.openpgp.org`; we don't fetch
  keys from `keyserver.ubuntu.com`. If you need a public key
  for someone not listed here, use one of those services.
- **Not** a revocation authority. If you believe an x-cmd key
  has been compromised, contact the team directly through the
  channels listed on [x-cmd.com](https://x-cmd.com), not via this
  repo.
- **Not** a signature archive. Signed commits and releases live
  in the upstream repos they sign; this repo only publishes the
  *public half* of the keypair.
